# FFI를 위한 객체 기반 API

## 설명

Rust 타입을 다른 언어에 노출하는 FFI API를 설계할 때는 관용적인 Rust API 설계와 다른 기준을 적용해야 합니다. 외부 언어의 타입 시스템에는 Rust의 소유권과 수명 규칙이 그대로 표현되지 않기 때문입니다. 원문은 객체 기반 FFI API의 원칙을 다음 네 가지로 요약합니다.

1. **캡슐화된 타입은 Rust가 소유하고, 사용자가 수명을 관리하며, 내부 표현은 불투명하게 둡니다.** 사용자는 라이브러리의 생성·해제 함수로 객체의 생명주기를 제어하지만, 객체의 크기나 필드를 직접 다루지 않습니다.
2. **호출 사이에 주고받는 데이터 타입은 사용자가 소유하고, 표현은 투명하게 둡니다.** 라이브러리는 입력 데이터를 읽거나 결과 데이터를 반환하지만, 이 데이터의 메모리를 누가 할당하고 해제하는지는 계약으로 분명히 합니다.
3. **라이브러리의 동작은 캡슐화된 타입을 인자로 받는 함수로 제공합니다.** 외부 호출자는 내부 필드에 직접 접근하는 대신 공개된 함수로 작업합니다.
4. **관련 동작과 상태는 단순한 구조보다 소유 관계와 수명에 따라 타입으로 묶습니다.** 외부 언어에 Rust의 빌림 수명을 직접 표현하게 하기보다, 연관된 객체의 수명 경계를 하나의 외부 객체 안에서 관리합니다.

## 동기

Rust는 여러 ABI를 통해 다른 언어와 상호 운용할 수 있는 FFI 기능을 제공합니다. 잘 설계된 Rust FFI는 외부 언어, 특히 C에서 익숙한 API 형태를 따르면서도 Rust 내부 구현을 필요 이상으로 불안전하게 만들지 않아야 합니다. 원문이 제시하는 목표는 다음과 같습니다.

1. 대상 언어에서 API를 쉽게 사용할 수 있어야 합니다.
2. 외부 API 형태 때문에 Rust 구현에 불필요한 `unsafe`가 강제되지 않아야 합니다.
3. 메모리 안전성 위반과 Rust의 정의되지 않은 동작(undefined behavior)이 발생할 가능성을 가능한 한 작게 유지해야 합니다.

Rust 구현은 경계에서 외부 언어가 전달하는 메모리와 호출 규약을 어느 정도 신뢰해야 합니다. 외부에서 잘못된 포인터를 전달하면 잘못된 메모리 접근으로 프로그램이 중단될 수 있고, 그 포인터를 Rust의 `unsafe` 코드가 잘못 조작하면 힙 손상과 같은 더 심각한 결과로 이어질 수 있습니다. 따라서 경계의 불안전한 가정을 줄이고, 호출자가 지켜야 하는 규칙을 작고 명확하게 만드는 API가 중요합니다.

객체 기반 API는 이 목적을 위해 Rust 내부의 상태를 불투명한 핸들 뒤에 두고, `unsafe` 구현과 외부의 안전한 호출 규칙을 구분하는 shim 계층을 만들도록 돕습니다.

## 예제: POSIX DBM API

원문은 파일 기반 데이터베이스 인터페이스인 [POSIX DBM](https://web.archive.org/web/20210105035602/https://www.mankier.com/0p/ndbm.h)을 객체 기반 API의 사례로 사용합니다. 아래는 핵심 선언을 설명하기 위해 C 문법을 읽기 쉽게 정리한 것입니다.

```c
struct DBM;

typedef struct {
    void *dptr;
    size_t dsize;
} datum;

int     dbm_clearerr(DBM *);
void    dbm_close(DBM *);
int     dbm_delete(DBM *, datum);
int     dbm_error(DBM *);
datum   dbm_fetch(DBM *, datum);
datum   dbm_firstkey(DBM *);
datum   dbm_nextkey(DBM *);
DBM    *dbm_open(const char *, int, mode_t);
int     dbm_store(DBM *, datum, datum, int);
```

이 인터페이스에는 두 가지 중요한 타입이 있습니다. 내부 상태를 캡슐화하는 `DBM`과 라이브러리와 사용자 사이에서 데이터를 교환하는 `datum`입니다.

### `DBM`: 불투명하고 캡슐화된 객체

`struct DBM;`은 구조체의 필드 정의가 없는 전방 선언(forward declaration)입니다. 외부 사용자는 `DBM`의 크기와 메모리 레이아웃을 알 수 없으므로 직접 생성하거나 필드에 접근할 수 없습니다. 대신 `dbm_open`이 데이터베이스 객체를 만들고 그 포인터를 반환합니다. 이후 모든 작업은 그 핸들을 인자로 받는 함수로 수행하며, 수명이 끝나면 `dbm_close`로 닫습니다.

즉, 객체의 실제 상태와 메모리는 라이브러리가 관리하고 사용자는 핸들의 생명주기를 관리합니다. 사용자는 `DBM` 내부의 크기나 배치를 알아야 할 필요가 없으며, 라이브러리는 구현을 바꾸더라도 외부의 자료구조 표현을 그대로 유지할 필요가 없습니다.

### `datum`: 투명한 데이터 교환 타입

`datum`은 바이트를 가리키는 포인터 `dptr`과 그 바이트 수 `dsize`를 담습니다. 데이터의 구체적인 형식은 정해져 있지 않으므로, C의 `void *`는 이 인터페이스가 임의의 사용자 데이터 바이트를 다룬다는 뜻입니다. 라이브러리는 데이터가 정수인지 구조체인지 해석할 필요 없이 포인터와 길이를 통해 값을 저장하거나 반환할 수 있습니다.

`datum`의 필드가 공개되어 있으므로 외부 사용자는 표현을 알고 데이터를 전달할 수 있습니다. 그러나 `dptr`이 가리키는 메모리의 소유권과 수명은 별도로 정의해야 합니다. 입력 `datum`은 호출자가 소유한 메모리를 가리키도록 하고, `dbm_fetch`처럼 라이브러리가 결과 데이터를 만들어 돌려주는 경우에는 할당 방법과 해제 책임을 문서화해야 합니다. 원문이 강조하는 안전한 설계 방향은 투명하게 노출되는 데이터의 소유권을 호출자에게 명확히 이전하는 것입니다. 예를 들어 양쪽이 호환되는 할당기를 사용하는지, 반환 버퍼를 어떤 함수로 해제해야 하는지를 API 계약으로 정해야 합니다.

C의 포인터는 Rust의 수명 표기와 마찬가지로 “이 메모리를 얼마나 오래 사용할 수 있는가”라는 계약을 내포하지만, C 컴파일러가 그 계약을 추적해 주지는 않습니다. 올바른 사용을 위해 호출자는 문서를 읽어야 하므로, API는 사용자가 잘못 다뤘을 때의 결과가 큰 모호함을 줄이고 소유권 이전을 쉽게 이해할 수 있도록 설계해야 합니다.

## 장점

객체 기반 API는 사용자가 반드시 지켜야 하는 메모리 안전성 규칙을 비교적 작고 분명한 범위로 줄입니다. DBM 예제에서 호출자가 지켜야 하는 핵심 규칙은 다음과 같습니다.

1. `dbm_open`이 반환한 유효한 핸들만 사용합니다. 임의의 포인터를 핸들인 것처럼 전달하면 잘못된 접근이나 메모리 손상이 발생할 수 있습니다.
2. `dbm_close`로 닫은 뒤에는 해당 핸들로 어떤 함수도 호출하지 않습니다. 닫힌 객체에 접근하면 use-after-free가 발생할 수 있습니다.
3. `datum.dptr`은 널 포인터이거나, `dsize`가 나타내는 길이만큼 유효한 메모리를 가리켜야 합니다.

이 방식은 포인터의 출처와 소유권을 추적하기 어렵게 만드는 문제도 줄여 줍니다. 특히 Rust에서 안전하게 표현되는 반복자의 수명 관계를 C API로 옮기는 상황에서 차이가 분명해집니다.

## 반복자의 수명과 FFI 경계

Rust에서는 반복자가 소유자보다 오래 살 수 없도록 수명 매개변수로 관계를 표현할 수 있습니다.

```rust,ignore
struct Dbm {
    /* ... */
}

impl Dbm {
    pub fn keys<'it>(&'it self) -> DbmKeysIter<'it> {
        /* ... */
    }
}

struct DbmKeysIter<'it> {
    owner: &'it Dbm,
}

impl<'it> Iterator for DbmKeysIter<'it> {
    /* ... */
}
```

`DbmKeysIter<'it>`은 `&'it Dbm`을 빌리므로, 컴파일러는 반복자가 원본 `Dbm`보다 오래 살아남지 않도록 검사합니다. 이는 안전하고 관용적인 Rust 인터페이스입니다.

하지만 이를 C에 단순하게 옮겨 `Dbm` 포인터를 받아 별도의 반복자 포인터를 돌려주는 API를 만들면, Rust의 `'it` 수명 관계는 ABI 경계에서 사라집니다.

```rust,ignore
#[no_mangle]
pub extern "C" fn dbm_iter_new(owner: *const Dbm) -> *mut DbmKeysIter {
    // 원문에서 수명 관계가 사라지는 문제를 설명하기 위한 나쁜 API 예시입니다.
}

#[no_mangle]
pub extern "C" fn dbm_iter_next(
    iter: *mut DbmKeysIter,
    key_out: *mut datum,
) -> libc::c_int {
    // 호출자는 owner와 iter의 상대적인 수명을 직접 맞춰야 합니다.
}

#[no_mangle]
pub extern "C" fn dbm_iter_del(iter: *mut DbmKeysIter) {
    // ...
}
```

C 호출자는 반복자를 만든 뒤 원본 DBM을 먼저 닫고도 반복자 함수를 호출할 수 있습니다. 이때 반복자는 이미 해제된 객체를 참조할 수 있으며, 읽기 오류뿐 아니라 초기화되지 않은 메모리 접근이나 정의되지 않은 동작으로 이어질 수 있습니다. Rust에서 표현되던 소유자와 반복자 사이의 제약이 포인터만으로 구성된 외부 API에서는 자동으로 유지되지 않습니다.

원문은 다음과 같은 의도적으로 결함이 있는 C 흐름으로 문제를 설명합니다. 아래는 가상의 `dbm_iter_*` API를 가정한 개략 코드이며, 실제 사용을 위한 구현이 아닙니다.

```c
int count_key_sizes(DBM *db) {
    /* 의도적으로 결함이 있는 흐름을 보여 주는 예제 */
    datum key;
    int total_size = 0;
    DBMIter *iter = dbm_iter_new(db);

    if (iter == NULL) {
        dbm_close(db);
        return -1;
    }

    int result;
    while ((result = dbm_iter_next(iter, &key)) >= 0) {
        free(key.dptr);
        total_size += key.dsize;

        if (result == 0) { /* 반복 종료 표시 */
            dbm_close(db);
        }
    }

    dbm_iter_del(iter);
    return result >= 0 ? -1 : total_size;
}
```

이 코드에서는 `result == 0`이 반복 종료를 뜻하는데, 데이터베이스를 닫은 뒤 반복문을 빠져나오지 않습니다. 다음 반복 조건에서 `dbm_iter_next`를 다시 호출하므로 이미 닫힌 `DBM`을 통해 반복자를 사용하게 됩니다. 올바른 제어 흐름이라면 종료를 확인한 즉시 반복을 끝내야 하지만, 이런 종료 조건 누락은 실제 FFI 호출 코드에서 객체의 수명 버그로 이어질 수 있습니다.

오류가 발생하지 않고 대부분 동작하는 것처럼 보여도 안전하다는 뜻은 아닙니다. 해제된 메모리가 즉시 다른 용도로 재사용되지 않으면 내부 검사가 우연히 실패를 반환할 수 있지만, 어떤 실행에서는 잘못된 메모리 접근이나 힙 손상으로 나타날 수 있습니다. 외부 코드가 핸들의 수명을 지키도록 문서에만 의존하면 Rust는 그 잘못된 호출을 막을 수 없습니다.

## 소유 관계를 한 객체로 통합하기

POSIX DBM API는 반복자 핸들을 별도로 노출하는 대신, 순회 동작을 부모 `DBM` 객체의 함수로 제공합니다.

```c
datum dbm_firstkey(DBM *);
datum dbm_nextkey(DBM *);
```

현재 반복 상태가 `DBM` 객체 안에 포함되므로, 반복 작업은 항상 같은 핸들을 통해 이루어집니다. 호출자는 별도의 반복자 객체를 데이터베이스보다 오래 보관할 수 없습니다. 즉, 반복자의 수명을 부모 객체와 같은 경계 안으로 합칩니다.

이 API는 한 `DBM` 객체에 반복 상태 하나만 두므로, 같은 데이터베이스에서 독립된 여러 반복자를 동시에 사용하는 기능은 제한됩니다. 이는 안전성을 위해 표현력을 일부 양보한 설계입니다. 이 제약이 실제 사용 사례에 적절한지는 API 사용자의 요구와 안전성 목표를 함께 고려해 판단해야 합니다.

## 단점과 고려 사항

- **API 표현력이 제한될 수 있습니다.** POSIX DBM 방식에서는 객체마다 반복 상태가 하나뿐이므로, 같은 객체를 순회하는 반복자를 여러 개 독립적으로 유지하기 어렵습니다. 안전한 대신 일반적인 Rust 반복자보다 제약이 큽니다.
- **설계 비용이 증가할 수 있습니다.** 서로 다른 객체와 수명이 얽혀 있다면 어떤 상태를 하나의 핸들에 묶고 어떤 관계를 외부에 노출할지 결정하는 데 상당한 설계 작업이 필요할 수 있습니다.
- **모든 API에 같은 패턴을 적용할 수 있는 것은 아닙니다.** 호출자의 언어, 사용 사례, 기대하는 동시성·반복 동작에 따라 별도의 핸들 설계가 더 적절할 수 있습니다. 다만 외부 포인터를 반환하는 경우 호출자가 지켜야 할 수명 규칙을 명시하고 검증하는 것이 중요합니다.

이 장의 다른 패턴은 관련 문제를 보완합니다.

- [래퍼로 타입 통합하기](/docs/ffi-wrapper-types)는 여러 Rust 타입과 상태를 하나의 불투명 객체로 묶습니다.
- [FFI에서 오류 처리하기](/docs/ffi-errors)는 정수 오류 코드와 센티널 반환값 등 외부 언어에 적합한 오류 전달 방식을 다룹니다.
- [FFI에서 문자열 받기](/docs/ffi-accept-strings)는 문자열 입력을 최소한의 `unsafe`로 처리하는 방법을 설명합니다.
- [FFI로 문자열 전달하기](/docs/ffi-pass-strings)는 문자열을 외부 함수에 전달할 때 소유권과 수명을 유지하는 방법을 설명합니다.
