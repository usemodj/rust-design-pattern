# 래퍼로 타입 통합하기

## 설명

이 패턴은 서로 연관된 여러 타입을 FFI 경계에서 하나의 래퍼 객체로 다루어 메모리 안전하지 않은 API 표면을 줄이는 방법입니다. Rust는 타입 사이의 별칭 규칙과 수명을 이용해 여러 접근 방식이 메모리 안전하고 데이터 경합을 일으키지 않도록 검사합니다. 하지만 Rust 타입을 다른 언어에 내보낼 때는 보통 이 타입들이 포인터로 표현됩니다. 포인터만으로는 원래 타입 사이의 수명 관계가 표현되지 않으므로, 호출자가 참조 대상의 유효 기간을 직접 지켜야 합니다.

외부 언어의 호출자가 포인터를 닫힌 객체에 사용하지 않도록 어느 정도 신뢰해야 합니다. 그러나 API의 모양에 따라 호출자가 지켜야 할 규칙의 수와 복잡성은 크게 달라집니다. 위험을 줄이는 방법 중 하나는 한 객체와 관련된 동작을 하나의 불투명한 래퍼 타입 안에 모으는 것입니다. 이때 외부 API를 위해 Rust 내부 API 전체를 부자연스럽게 바꾸지 않고, 외부 경계에서만 래퍼를 사용할 수 있습니다.

## 예제: 컬렉션 순회

외부 언어에 컬렉션의 키를 순회하는 기능을 제공한다고 가정해 봅시다. 인터페이스의 동작은 다음과 같습니다.

1. `first_key`를 호출해 순회를 시작합니다.
2. `next_key`를 호출할 때마다 다음 키로 이동합니다.
3. 이미 마지막 항목에 도달한 뒤 `next_key`를 호출하면 더 진행하지 않습니다.
4. 반복자 상태를 별도 객체로 노출하는 대신 컬렉션을 감싼 래퍼 안에 둡니다.

이터레이터가 `nth()`를 효율적으로 구현한다면, 다음처럼 현재 위치만 저장하고 함수가 호출될 때마다 임시 이터레이터를 만들 수 있습니다.

```rust,ignore
struct MySetWrapper {
    myset: MySet,
    iter_next: usize,
}

impl MySetWrapper {
    pub fn first_key(&mut self) -> Option<&Key> {
        self.iter_next = 0;
        self.next_key()
    }

    pub fn next_key(&mut self) -> Option<&Key> {
        if let Some(next) = self.myset.keys().nth(self.iter_next) {
            self.iter_next += 1;
            Some(next)
        } else {
            None
        }
    }
}
```

`MySetWrapper`가 컬렉션과 현재 순회 위치를 함께 소유합니다. `first_key`는 위치를 처음으로 되돌리고 첫 항목을 요청하며, `next_key`는 현재 위치의 항목을 얻은 뒤 위치를 증가시킵니다. 이 설계에서는 컬렉션을 빌리는 이터레이터를 여러 FFI 호출 사이에 보관하지 않으므로 래퍼 자체에 `unsafe` 코드가 필요하지 않습니다.

이 예제는 래퍼 구조를 설명하는 Rust 코드이며, 그대로 C ABI에 노출하는 완성된 함수는 아닙니다. 실제 FFI에서 `&Key` 참조를 그대로 반환할 수는 없으므로, 키를 호출자 버퍼에 복사할지, 명시적인 소유권 이전으로 반환할지, 다음 호출 전까지만 유효한 포인터로 제공할지 API 계약을 정해야 합니다. 또한 외부 코드가 키를 사용하는 동안 컬렉션을 수정할 수 있는지도 정의해야 합니다.

`nth(index)`가 앞에서부터 요소를 세어 이동하는 구현이라면 매번 처음부터 다시 순회하므로 전체 순회가 비효율적일 수 있습니다. 원문도 `nth()`가 효율적인 경우를 전제로 합니다. 실제 컬렉션의 반복자 비용을 확인하고, 필요하면 외부 API 전용으로 효율적인 커서나 순회 방식을 설계하세요.

## 장점

연관된 타입들의 수명 관계를 하나의 핸들 안에 감추면, 외부 사용자는 원본 컬렉션과 이터레이터의 상대적인 수명을 별도로 관리할 필요가 줄어듭니다. 이 방식은 다른 객체 기반 API 설계와 마찬가지로 use-after-free와 같은 잘못된 사용 가능성을 낮추고, Rust 쪽에서 소유권과 상태를 관리할 수 있게 합니다.

객체 기반 FFI API의 전반적인 장점과 주의점은 [FFI를 위한 객체 기반 API](/docs/ffi-object-apis)를 참고하세요.

## 단점

서로 연관된 타입을 하나로 래핑하는 작업은 쉽지 않을 수 있습니다. 때로는 외부 API의 요구에 맞춰 Rust API를 어느 정도 조정하는 편이 더 간단할 수도 있습니다. 다만 외부 호출 편의를 위해 Rust의 안전성 보장을 약화시키는 방식은 피해야 합니다.

예를 들어 이터레이터의 `nth()`가 효율적이지 않다면, 매 호출마다 순회를 처음부터 다시 하는 대신 래퍼가 반복 상태를 직접 관리하거나 FFI 전용의 효율적인 접근 방식을 제공할 수 있습니다. 순회 중 컬렉션을 변경할 때 현재 위치가 어떻게 되는지도 정의해야 합니다.

## 이터레이터를 래퍼 안에 직접 저장하려다 실패하기

모든 종류의 이터레이터를 래퍼에 넣으려면, C 코드에서 하듯 이터레이터의 수명을 지우고(lifetime erasure) 수명을 수동으로 관리하고 싶을 수 있습니다. 하지만 Rust에서 참조가 빌린 대상보다 오래 살지 않는다는 보장을 없애는 일은 매우 어렵고, 한 가지 문제를 해결해도 다른 동작이 별칭 규칙을 위반할 수 있습니다.

위 래퍼에 이터레이터 자체를 넣으려는 형태는 다음과 같을 수 있습니다.

```rust,ignore
struct MySetWrapper {
    myset: MySet,
    iter_next: usize,
    // transmute로 수명을 늘린 Box<KeysIter<'self>>에서 만들어졌다고 가정
    iterator: Option<NonNull<KeysIter<'static>>>,
}
```

이 아이디어는 `transmute`로 이터레이터의 수명을 `'static`으로 늘리고, 포인터 안에 숨겨 둡니다. 하지만 이는 원래 보장되어야 하는 “이터레이터는 빌린 컬렉션보다 오래 살 수 없다”는 관계를 타입 시스템에서 제거할 뿐입니다. 포인터가 존재한다는 사실만으로 수명 문제가 해결되는 것은 아닙니다.

더 심각한 문제는 이터레이터가 살아 있는 동안 래퍼의 다른 함수를 호출해 내부 컬렉션을 변경할 수 있다는 점입니다. 예를 들어 순회 중인 키에 새 값을 저장하는 동작을 제공한다고 합시다.

```rust,ignore
pub mod unsafe_module {
    // 다른 모듈 내용 생략

    pub fn myset_store(
        myset: *mut MySetWrapper,
        key: datum,
        value: datum,
    ) -> libc::c_int {
        // 문제를 보여 주기 위한 잘못된 예제입니다. 실제 코드에 사용하지 마세요.
        let myset: &mut MySet = unsafe {
            // SAFETY: 이 시점에 이터레이터가 컬렉션을 공유 참조 중일 수 있습니다.
            &mut (*myset).myset
        };

        /* ...키와 값의 유효성을 확인하고 변환... */

        match myset.store(casted_key, casted_value) {
            Ok(_) => 0,
            Err(error) => error.into(),
        }
    }
}
```

이터레이터가 존재하는 동안 `myset_store`가 `&mut MySet`을 만들면, 이 가변 참조가 `MySet`에 독점적으로 접근한다고 주장하게 됩니다. 반면 저장된 이터레이터는 같은 컬렉션을 공유 참조하고 있습니다. 가변 참조의 독점성 조건과 기존 공유 참조가 충돌하므로 이 코드는 정의되지 않은 동작을 일으킬 수 있습니다. 이터레이터가 바로 그 순간 컬렉션을 읽고 있지 않더라도 참조의 유효 기간과 별칭 규칙은 유지되어야 합니다.

이 문제를 피하려면 가변 접근을 하기 전에 이터레이터가 가진 공유 참조를 확실히 제거하고, 변경 작업 후 필요하다면 이터레이터를 다시 구성해야 합니다. 그러나 모든 별칭과 수명 조건을 안전하게 관리하기가 복잡하며, 일부 경우에는 C 구현보다 비효율적일 수 있습니다. 이터레이터를 지우는 트릭을 먼저 찾기보다, 위치 인덱스처럼 빌린 참조를 보관하지 않는 상태 표현이나 호출마다 안전하게 계산되는 접근 방식을 우선 고려하세요.

C가 이런 방식으로 더 효율적으로 보일 수 있는 이유는 C 포인터에는 Rust의 참조 별칭 규칙이 같은 방식으로 강제되지 않기 때문입니다. 그 자유에는 대가가 있으며, C 라이브러리는 특정 상황에서 스레드 안전하지 않다고 문서화해야 하는 경우가 흔합니다. Rust는 메모리 안전성과 그에 기반한 최적화를 보장하는 대신, 일부 포인터 조작을 허용하지 않습니다.
