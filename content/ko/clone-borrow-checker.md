# 빌림 검사기를 만족시키기 위한 무분별한 Clone

## 설명

Rust의 빌림 규칙은 하나의 값에 대해 가변 참조를 하나만 허용하거나, 여러 개의 불변 참조만 동시에 허용합니다. 이 규칙은 데이터 경합과 메모리 안전성 문제를 막아 줍니다.

빌림 검사기 오류를 만났을 때 원인을 살펴보지 않고 `.clone()`을 추가해 컴파일을 통과시키는 것이 이 안티 패턴입니다. 복제는 기존 값을 빌리는 것이 아니라 복제본을 만들기 때문에 빌림 충돌이 사라질 수 있습니다. 하지만 그 결과가 프로그램의 소유권 의도와 맞지 않거나, 불필요한 메모리·연산 비용을 발생시킬 수 있습니다.

## 원문 예제

원문의 예제는 정수 `x`를 복제한 뒤 복제본을 가변 참조로 빌립니다. 따라서 `x` 자체는 빌리지 않은 채 계속 사용할 수 있습니다.

```rust,ignore
fn main() {
    let mut x = 5;

    // x를 먼저 복제한 뒤 그 복제본을 가변 대여합니다.
    let y = &mut (x.clone());

    // x 자체는 빌리지 않았으므로 사용할 수 있습니다.
    println!("{x}");

    // y가 실제로 사용되도록 복제본을 변경합니다.
    *y += 1;
}
```

`i32`는 `Copy` 타입이므로 여기서 복제는 저렴한 값 복사입니다. 하지만 이 기법을 `String` 같은 소유 타입에 적용하면 문자열 버퍼와 내용을 복사할 수 있습니다. 원본과 복제본은 독립된 값이므로 한쪽을 변경해도 다른 쪽에는 반영되지 않습니다. 컴파일 오류가 사라졌다는 사실만으로 원래 의도한 데이터를 수정하고 있다고 보장되지는 않습니다.

## 먼저 빌리는 인터페이스를 고려하기

함수가 값을 보관하거나 소유해야 하는 것이 아니라 잠시 읽기만 한다면, 값을 전달하는 대신 참조를 받도록 바꾸는 편이 더 적절할 수 있습니다.

```rust
fn print_length(value: &str) {
    println!("{}", value.len());
}

fn main() {
    let name = String::from("Ferris");
    print_length(&name);
    println!("{name}");
}
```

이 방식에서는 함수가 `name`의 소유권을 가져가지 않으므로 호출 뒤에도 원래 문자열을 사용할 수 있습니다. Rust의 참조는 소유권을 이전하지 않으면서 값에 접근하도록 하며, 빌림 검사기는 참조가 유효한 기간을 확인합니다.

함수나 메서드가 정말 소유권을 가져야 하는지 확인하고, 그렇지 않다면 `&T`, `&mut T` 또는 문자열의 경우 `&str`처럼 빌린 타입을 받게 할 수 있는지 살펴보세요.

## 복제가 타당한 경우

`.clone()`이 보인다고 해서 무조건 잘못된 것은 아닙니다. 다음과 같은 경우에는 복제가 의도에 맞을 수 있습니다.

- 복제본을 원본과 독립적으로 소유하고 이후에 별도로 변경해야 합니다.
- 값이 작고 복제 비용이 낮으며, 복사 의도가 분명합니다.
- 소유권과 수명 관계를 복잡하게 만드는 것보다, 비용이 허용되는 범위에서 단순한 코드를 선택하는 편이 낫습니다.
- 프로토타입이나 해커톤 코드처럼 성능·메모리 사용량이 엄격한 요구사항이 아니고, 우선 동작을 확인하는 것이 중요합니다.
- 빌림 규칙을 만족시키는 대안이 지나치게 복잡해 읽기 쉬운 구현이 더 중요하다고 판단했습니다.

이 경우에도 복제가 왜 필요한지 이해하고 결정하세요. 성능이 중요해지는 시점에는 실제 사용 사례를 측정한 뒤 개선하는 것이 막연하게 복제를 피하거나 조기에 최적화하는 것보다 나을 수 있습니다.

## `Rc<T>`와 `Arc<T>`의 Clone

참조 카운팅 포인터의 `.clone()`은 일반적인 소유 타입의 복제와 다릅니다. `Rc<T>`를 복제하면 힙에 저장된 `T` 전체를 복사하는 대신 같은 할당을 가리키는 `Rc` 핸들이 하나 더 만들어지고 참조 카운트가 증가합니다. `Arc<T>`도 같은 공유 소유권을 제공하지만, 참조 카운트를 원자적으로 관리해 여러 스레드에서 사용할 수 있습니다.

```rust
fn main() {
    use std::rc::Rc;
    use std::sync::Arc;

    let local = Rc::new(String::from("shared in one thread"));
    let local_handle = Rc::clone(&local);
    assert!(Rc::ptr_eq(&local, &local_handle));

    let shared = Arc::new(String::from("shared across threads"));
    let shared_handle = Arc::clone(&shared);
    assert!(Arc::ptr_eq(&shared, &shared_handle));
}
```

이 예제의 복제는 같은 힙 할당을 공유하는 핸들을 만듭니다. 공유 데이터 자체를 수정할 수 있는 것은 아니며, 변경이 필요하다면 `RefCell`, `Mutex`, `RwLock` 같은 내부 가변성·동기화 도구를 별도로 고려해야 합니다. 또한 `Arc<T>`를 쓴다고 임의의 `T`가 자동으로 스레드 안전해지는 것은 아닙니다. `T`와 접근 방식이 해당 스레드 안전성 조건을 만족해야 합니다.

## 빌림 충돌을 만났을 때 살펴볼 대안

1. **필요한 참조만 받습니다.** 함수가 구조체 전체를 받을 필요가 없다면 필요한 필드만 받거나, `&T`·`&mut T`를 받도록 인터페이스를 좁힙니다.
2. **빌림이 겹치는 구간을 줄입니다.** 참조가 실제로 필요한 범위를 확인하고, 불필요하게 오래 유지되는 참조를 사용하지 않도록 코드의 순서와 범위를 정리합니다.
3. **독립적인 상태를 구조적으로 나눕니다.** 큰 구조체의 서로 다른 책임을 별도 타입으로 분리하면 필요한 필드만 독립적으로 빌릴 수 있습니다. 자세한 내용은 [독립적으로 빌리기 위한 구조체 분해](/docs/compose-structs)를 참고하세요.
4. **소유권을 옮기거나 대체합니다.** 값을 복제하지 않고 꺼내야 하는 상황에서는 `mem::take`, `mem::replace`, `Option::take`가 더 적절할 수 있습니다. [값을 바꾸면서 소유권 유지하기](/docs/mem-take-replace)를 참고하세요.
5. **공유 소유권이 실제 요구인지 확인합니다.** 여러 소유자가 같은 값을 보유해야 하는 경우에는 단순 복제보다 `Rc<T>` 또는 `Arc<T>`가 의도를 잘 표현할 수 있습니다. 다만 참조 카운팅과 공유 접근 비용이 추가됩니다.

이 대안들은 모든 상황에서 복제보다 우월한 것이 아닙니다. 값의 소유자가 누구인지, 데이터가 언제까지 필요한지, 각 사용자가 독립된 사본을 가져야 하는지 먼저 정하고 선택하세요.

## Clone 사용을 점검하는 방법

복제가 불필요한 것으로 의심되면 프로젝트에서 `cargo clippy`를 실행해 보세요. Clippy는 불필요한 복제와 관련된 일부 사례를 포함해 여러 흔한 실수를 찾아낼 수 있습니다. 다만 모든 불필요한 Clone을 자동으로 판별할 수 있는 것은 아니므로, 진단 결과와 실제 소유권 의도를 함께 검토해야 합니다.
