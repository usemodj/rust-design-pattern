# 디자인 원칙

설계 원칙은 모든 상황에 적용되는 법칙이라기보다 설계의 결과를 점검하는 질문입니다. 원칙을 기계적으로 적용하기보다 무엇을 단순화하고 무엇을 희생하는지 따져 보세요.

## SOLID

- **단일 책임(SRP):** 모듈이나 타입은 하나의 일관된 변경 이유를 갖도록 합니다.
- **개방-폐쇄(OCP):** 기존 코드를 계속 수정하지 않고도 필요한 확장이 가능하도록 경계를 설계합니다.
- **리스코프 치환(LSP):** 구현은 타입이 약속한 계약을 지켜야 합니다.
- **인터페이스 분리(ISP):** 사용자가 필요하지 않은 기능까지 의존하지 않게 합니다.
- **의존성 역전(DIP):** 상위 정책이 구체 구현 세부 사항에 직접 묶이지 않도록 추상화 경계를 둡니다.

Rust에서는 트레이트, 모듈의 공개 범위, 제네릭 등을 조합해 이런 경계를 표현할 수 있습니다. 모든 작은 타입에 트레이트를 추가할 필요는 없습니다.

## 합성, 재사용, 단순성

- **합성을 상속보다 우선:** 동작을 필드와 작은 구성 요소로 조합합니다. Rust에는 구조체 상속이 없으며 트레이트와 합성이 일반적인 대안입니다.
- **DRY(반복하지 않기):** 같은 지식이나 규칙이 여러 곳에 복제되어 함께 바뀌어야 하는지 확인합니다. 비슷해 보이는 코드까지 무조건 합치지는 마세요.
- **KISS:** 이해하기 쉬운 가장 단순한 해법을 우선합니다.
- **YAGNI:** 아직 요구되지 않은 기능을 미리 만들지 않습니다.

## 경계와 계약

- **데메테르 법칙:** 한 구성 요소가 지나치게 많은 다른 객체의 내부 구조를 알지 않도록 합니다.
- **계약에 의한 설계:** 함수의 선행 조건, 결과, 실패 조건을 명시하고 타입과 문서로 전달합니다.
- **캡슐화:** 불변식을 지키는 데 필요한 상태를 숨기고 안전한 연산만 노출합니다.
- **명령-질의 분리(CQS):** 상태를 바꾸는 명령과 값을 읽는 질의를 가능한 한 구분합니다.
- **최소 놀람 원칙:** API의 이름과 동작이 사용자의 합리적인 기대에 맞아야 합니다.

## 언어와 모듈의 단위

API는 호출자가 읽고 작성하기 쉬운 단위로 구성하고, 값에 접근하는 방법은 불필요하게 놀랍지 않게 유지하세요. 데이터를 직렬화·복원하거나 프로세스 경계를 넘는다면, 수명이나 내부 표현에 기대지 말고 명시적인 영속 형식을 정의하는 편이 안전합니다.
